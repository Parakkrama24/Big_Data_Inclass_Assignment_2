## System Overview

This is a production-ready Kafka-based order processing system that demonstrates enterprise messaging patterns including:
- **Schema-based serialization** using Apache Avro
- **Real-time stream processing** with aggregations
- **Fault tolerance** with retry mechanisms
- **Error handling** with Dead Letter Queue pattern
- **Schema evolution** support via Schema Registry

### Business Use Case
The system simulates an e-commerce order processing pipeline where:
- Orders are generated by the producer service
- Orders are consumed and processed in real-time
- Running statistics (average price) are calculated
- Failed orders are automatically retried
- Permanently failed orders are isolated for investigation

## Components Explained

### 1. Infrastructure Layer (Docker Compose)

#### Zookeeper (Port 2181)
- **Purpose**: Cluster coordination for Kafka
- **Role**: Manages Kafka broker metadata, leader election
- **Image**: `confluentinc/cp-zookeeper:7.5.1`

#### Kafka Broker (Port 9092)
- **Purpose**: Distributed message broker
- **Role**: Stores and serves messages, manages topics and partitions
- **Image**: `confluentinc/cp-kafka:7.5.1`
- **Configuration**:
  - `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR=1`
  - `KAFKA_AUTO_CREATE_TOPICS_ENABLE=true`

#### Schema Registry (Port 8081)
- **Purpose**: Centralized Avro schema management
- **Role**: Version control for message schemas, ensures compatibility
- **Image**: `confluentinc/cp-schema-registry:7.5.1`
- **API Endpoint**: `http://localhost:8081`

### 2. Application Layer

#### Order Producer (`OrderProducer.java`)

**Responsibilities:**
- Generate random order messages
- Serialize orders using Avro schema
- Send messages to Kafka topic
- Handle acknowledgments

**Key Configuration:**
```java
acks=all                    // Wait for all replicas
retries=3                   // Retry failed sends
enable.idempotence=true     // Exactly-once semantics
```

**Message Generation:**
- 10 different products (Laptop, Phone, Tablet, etc.)
- Random prices between $10-$1010
- Sequential order IDs starting from 1001
- 1-second delay between messages for readability

**Code Structure:**
```java
OrderProducer
├── Constructor: Initialize KafkaProducer with configs
├── produceOrders(): Generate and send N orders
├── close(): Cleanup resources
└── main(): Entry point with shutdown hook
```

#### Order Consumer (`OrderConsumer.java`)

**Responsibilities:**
- Consume orders from Kafka topic
- Deserialize Avro messages
- Calculate real-time running average
- Implement retry logic
- Send failed messages to DLQ

**Key Configuration:**
```java
group.id=order-consumer-group
enable.auto.commit=false      // Manual offset management
auto.offset.reset=earliest    // Process from beginning
max.poll.records=10           // Batch size
```

**Processing Pipeline:**
```
Message Received
    ↓
Deserialize Avro
    ↓
Process Order (with 10% failure simulation)
    ↓
    ├─ Success → Update Aggregation → Commit Offset
    │
    └─ Failure → Retry Logic
                    ├─ Attempt 1 (wait 1s) → Retry
                    ├─ Attempt 2 (wait 2s) → Retry
                    ├─ Attempt 3 (wait 3s) → Retry
                    └─ Max retries → Send to DLQ
```

**Code Structure:**
```java
OrderConsumer
├── Constructor: Initialize consumer and DLQ producer
├── createConsumer(): Setup Kafka consumer config
├── createDlqProducer(): Setup DLQ producer
├── processOrder(): Main processing logic + aggregation
├── handleRetry(): Exponential backoff retry mechanism
├── sendToDlq(): Dead letter queue handler
├── consume(): Main polling loop
└── close(): Cleanup and statistics
```

### 3. Data Model

#### Avro Schema (`order.avsc`)
```json
{
  "namespace": "com.bigdata.kafka.avro",
  "type": "record",
  "name": "Order",
  "fields": [
    {"name": "orderId", "type": "string"},
    {"name": "product", "type": "string"},
    {"name": "price", "type": "float"}
  ]
}
```

**Schema Benefits:**
- **Type Safety**: Compile-time validation
- **Compact**: Binary format, smaller than JSON
- **Evolution**: Schema Registry manages versions
- **Documentation**: Self-documenting structure

**Generated Java Class:**
- Immutable builder pattern
- Getters return `CharSequence` (Avro spec)
- Efficient serialization/deserialization

## Data Flow

### Message Production Flow

```
1. Producer Creates Order
   Order order = Order.newBuilder()
       .setOrderId("1001")
       .setProduct("Laptop")
       .setPrice(543.21f)
       .build();

2. Avro Serialization
   Schema Registry checks/registers schema
   Message serialized to binary Avro format

3. Send to Kafka
   ProducerRecord<String, Order> created
   Key: orderId (for partitioning)
   Value: Order object

4. Kafka Stores Message
   Persisted to disk
   Replicated (if configured)
   Offset assigned

5. Acknowledgment
   Producer receives metadata:
   - Partition number
   - Offset number
   - Timestamp
```

### Message Consumption Flow

```
1. Consumer Polls Kafka
   consumer.poll(Duration.ofMillis(1000))
   Returns batch of records

2. For Each Record:
   ├─ Avro Deserialization
   │  Schema Registry validates schema
   │  Binary → Order object
   │
   ├─ Processing
   │  ├─ Calculate running average
   │  └─ Update statistics
   │
   ├─ Error Handling
   │  └─ Simulated 10% failure
   │
   └─ Commit or Retry
      ├─ Success → Commit offset
      └─ Failure → Retry logic → DLQ

3. Offset Management
   Manual commit after successful batch processing
```

## Key Features Implementation

### 1. Real-Time Aggregation

**Running Average Calculation:**
```java
private double totalPrice = 0.0;
private int orderCount = 0;

// On each order
orderCount++;
totalPrice += order.getPrice();
double runningAverage = totalPrice / orderCount;
```

**Output Example:**
```
Order 1: Price=$543.21 | Avg=$543.21 (1 order)
Order 2: Price=$289.45 | Avg=$416.33 (2 orders)
Order 3: Price=$412.78 | Avg=$415.15 (3 orders)
```

### 2. Retry Logic with Exponential Backoff

**Implementation:**
```java
Map<String, Integer> retryAttempts = new HashMap<>();
int MAX_RETRY_ATTEMPTS = 3;

private void handleRetry(ConsumerRecord<String, Order> record, Exception e) {
    String key = record.key();
    int attempts = retryAttempts.getOrDefault(key, 0) + 1;

    if (attempts <= MAX_RETRY_ATTEMPTS) {
        retryAttempts.put(key, attempts);

        // Exponential backoff: 1s, 2s, 3s
        Thread.sleep(1000 * attempts);

        try {
            processOrder(record);  // Retry
            retryAttempts.remove(key);  // Success
        } catch (Exception retryException) {
            if (attempts >= MAX_RETRY_ATTEMPTS) {
                sendToDlq(record, retryException);
            }
        }
    }
}
```

**Backoff Strategy:**
- Attempt 1: Wait 1 second
- Attempt 2: Wait 2 seconds
- Attempt 3: Wait 3 seconds
- After 3 failures: Send to DLQ

### 3. Dead Letter Queue (DLQ)

**Purpose:**
- Isolate problematic messages
- Prevent blocking of message pipeline
- Enable manual investigation and reprocessing

**DLQ Message Format:**
```
Failed Order - ID: 1015, Product: Laptop, Price: 543.21
| Error: Simulated temporary processing failure
| Original Partition: 0, Offset: 14
```

**DLQ Producer:**
```java
private KafkaProducer<String, String> dlqProducer;

private void sendToDlq(ConsumerRecord<String, Order> record, Exception e) {
    String dlqMessage = String.format(
        "Failed Order - ID: %s, Product: %s, Price: %.2f | Error: %s",
        order.getOrderId(), order.getProduct(),
        order.getPrice(), e.getMessage()
    );

    ProducerRecord<String, String> dlqRecord =
        new ProducerRecord<>(DLQ_TOPIC, record.key(), dlqMessage);

    dlqProducer.send(dlqRecord).get();
}
```

### 4. Avro Serialization

**Producer Side:**
```java
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
          KafkaAvroSerializer.class.getName());
props.put("schema.registry.url", "http://localhost:8081");
```

**Consumer Side:**
```java
props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
          KafkaAvroDeserializer.class.getName());
props.put("schema.registry.url", "http://localhost:8081");
props.put(KafkaAvroDeserializerConfig.SPECIFIC_AVRO_READER_CONFIG, true);
```

**Schema Registry Interaction:**
1. Producer sends message → Serializer checks schema
2. If schema doesn't exist → Register in Schema Registry
3. Schema ID embedded in message header
4. Consumer receives message → Deserializer reads schema ID
5. Fetch schema from registry → Deserialize message

## Design Decisions

### 1. Why Avro over JSON?

**Advantages:**
- **Compact**: 30-50% smaller than JSON
- **Fast**: Binary format, no parsing overhead
- **Schema Evolution**: Built-in compatibility checking
- **Type Safety**: Compile-time validation
- **Documentation**: Schema serves as documentation

**Trade-offs:**
- Requires Schema Registry infrastructure
- Less human-readable than JSON
- Learning curve for schema definition

### 2. Why Manual Offset Commit?

**Benefits:**
- **At-least-once** delivery guarantee
- Control over when offsets are committed
- Prevents data loss on failures
- Can batch commits for efficiency

**Implementation:**
```java
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false");

// Process all records in batch
for (ConsumerRecord<String, Order> record : records) {
    processOrder(record);
}

// Commit only after successful processing
consumer.commitSync();
```

### 3. Why Exponential Backoff?

**Rationale:**
- Gives temporary issues time to resolve
- Reduces load on failing systems
- Industry-standard retry pattern
- Configurable retry intervals

**Alternative Approaches:**
- Fixed delay: Too aggressive or too slow
- Random jitter: Unpredictable
- No retry: Immediate failures

### 4. Why Separate DLQ Producer?

**Design Choice:**
```java
private final KafkaConsumer<String, Order> consumer;
private final KafkaProducer<String, String> dlqProducer;
```

**Reasoning:**
- Different serialization (String vs Avro)
- Independent configuration
- Fail-fast on DLQ errors
- Clear separation of concerns

### 5. Why Simulated Failures?

**Purpose:**
- Demonstrate retry logic in action
- Show DLQ functionality
- Test system resilience
- Educational demonstration

**Implementation:**
```java
if (Math.random() < 0.1) {  // 10% failure rate
    throw new Exception("Simulated temporary processing failure");
}
```

## Performance Considerations

### Scalability
- **Producer**: Can scale horizontally (multiple instances)
- **Consumer**: Scale within consumer group (partition-based)
- **Kafka**: Add more brokers for throughput

### Reliability
- **acks=all**: Ensures replication before acknowledgment
- **Idempotence**: Prevents duplicate messages
- **Manual commits**: At-least-once delivery

### Monitoring
- **Kafka metrics**: Broker, topic, consumer lag
- **Schema Registry**: Schema versions, compatibility
- **Application logs**: Processing rates, error rates
